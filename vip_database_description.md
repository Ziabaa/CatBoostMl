# База данных для прогноза VIP

> **Важно:** база может быть немного «мусорной». Она проектировалась быстро и только для тестов, поэтому в схеме есть недоработки (они перечислены в конце). Для боевого использования структуру нужно привести в порядок.

## Назначение

PostgreSQL-база (схема `public`) хранит данные пользователей, сделавших хотя бы одно пополнение (FTD), признаки для обучения модели прогноза VIP и разбиение пользователей на обучающую и тестовую выборки.

## Таблицы

| Таблица | Что хранит |
|---|---|
| `users_metrics` | **Главная таблица.** Одна строка на пользователя: `uid`, даты (FTD, регистрация, установка приложения), исходные показатели первого дня (депозиты, спины, ставки, чек, неудачные депозиты), email-домен, а также целевые поля `is_vip`, `ltv`, `dep_60_days` и флаг `use_for_training` |
| `user_financial_features` | Финансовые и игровые признаки первого дня: средняя ставка, число спинов, сумма депозитов, число транзакций, средний чек, неудачные депозиты. Связь 1:1 с `users_metrics` |
| `user_time_features` | Временные признаки: день месяца, период месяца, день недели, выходной, месяц, час FTD, часы от регистрации и от установки до FTD. Связь 1:1 с `users_metrics` |
| `types` | Справочник типов (названий) с возможностью иерархии через `type_id` на саму себя. Предположительно, это названия наборов или экспериментов (назначение выведено из схемы) |
| `user_training_types` | Связь «пользователь ↔ тип»: какие пользователи входят в обучающую выборку данного типа |
| `user_test_types` | Аналогичная связь для тестовой выборки |

## Как таблицы связаны

```
users_metrics (id)
 ├── user_financial_features (user_metrics_id)   1:1
 ├── user_time_features      (user_metrics_id)   1:1
 ├── user_training_types     (user_id) ──► types (type_id)
 └── user_test_types         (user_id) ──► types (type_id)
```

## Как использовать

- **Признаки модели** берутся из `user_financial_features` и `user_time_features`, плюс `email_domain` из `users_metrics`.
- **Целевая переменная:** `is_vip` (или `ltv ≥ 5000`).
- **Не использовать как признаки:** `is_vip`, `ltv`, `dep_60_days`. Это результаты, известные только позже, их использование вызовет утечку данных.
- Состав выборок задаётся через `user_training_types` и `user_test_types` по типу из `types`.

## Что в схеме «мусорное» и стоит поправить

1. В DDL `users_metrics` указана **дважды**, а в `types` и `user_financial_features` есть лишние служебные комментарии.
2. `users_metrics.uid` может быть пустым и не уникален, при этом в таблицах признаков `uid` уникален. Нужны `NOT NULL` и `UNIQUE` на `users_metrics.uid`.
3. В `user_test_types` нет внешнего ключа на `users_metrics`, а в `user_training_types` нет уникальности `(user_id, type_id)`. Один пользователь может попасть в выборку дважды или указывать на несуществующую строку.
4. Поле `use_for_training` дублирует смысл таблиц `user_training_types` и `user_test_types`. Нужно оставить один способ разбиения.
5. Колонка `uid` продублирована в таблицах признаков, хотя уже есть связь по `user_metrics_id`. В таблицах признаков повторяются поля `users_metrics`: финансовые колонки хранятся в обеих таблицах и могут разойтись.
6. Типы выбраны небрежно: `spins_count_ftd_day` — `float8` вместо целого, флаги (`ftd_is_weekend`, `is_vip`, `use_for_training`) — `int4` вместо `boolean`, смешаны `timestamp` и `timestamptz`, `uid` бывает `text` и `varchar(36)`.
7. Нет индексов (кроме ключей) на `uid`, `ftd_date`, `is_vip` и внешние ключи.
8. Нет поля горизонта и даты фиксации VIP: непонятно, за какой срок после FTD пользователь считается VIP.
